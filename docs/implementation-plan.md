# План реализации: фазы 1–10

Статус: ФАЗА 0. Порядок жёсткий (SPEC §3), каждая фаза заканчивается отчётом
и гейтом — стоп до подтверждения владельца. Код фазы N+1 не пишется, пока не
закрыт гейт N. DRY_RUN появляется в фазе 2 и живёт до самого конца.

Сквозные правила Definition of Done для КАЖДОЙ фазы:
- `ruff`, `mypy`, `bandit`, `pip-audit`, тесты — зелёные; команды в отчёте;
- ни один инвариант SPEC §2 не нарушен; чеклист SPEC §18 пройден;
- новые таблицы — миграции вверх и вниз; новые настройки — в `.env.example`
  и в админке; новые эндпоинты — `require_admin()` + response-модель +
  тест обхода роутов проходит;
- никаких заглушек в прод-путях; отчёт перечисляет, что осталось.

## ФАЗА 1 — Каркас

**Скоуп:** структура репозитория по SPEC §4; `pyproject.toml`; Docker Compose
(postgres+pgvector, redis, backend, worker, frontend) с лимитами, healthchecks,
non-root, digest-pinned образами; Alembic; конфиг через pydantic-settings с
fail-fast валидацией; structlog JSON-логи с correlation_id; `/healthz`;
CI-заготовка (ruff, mypy, bandit, pip-audit, gitleaks, trivy, npm audit,
тесты); Makefile (up, down, logs, migrate, test, lint, backup).
**Аутентификация целиком** (SPEC §10): таблицы admin_user / admin_sessions /
recovery-коды, argon2id, TOTP, серверные сессии в HttpOnly cookie, CSRF,
rate limit логина, lockout, `make create-admin` / `make reset-admin-password`,
падение при >1 активном админе, аудит попыток входа. Каркас фронтенда:
Vite + React + TS, логин-форма, layout с левым меню.

**DoD:** compose поднимается локально; `/healthz` отвечает; вход с
телефоном+паролем+TOTP работает; автоматический тест обхода `app.routes`
(401 всюду кроме `/healthz`); тесты: брутфорс-lockout, «пароль без TOTP —
не сессия», ревокация сессий при смене пароля, create-admin на непустой
таблице отказывает; в образах нет секретов.

## ФАЗА 2 — Транспорт GREEN-API

**Скоуп:** `WhatsAppProvider` (ABC) + `GreenApiProvider` (httpx, timeout,
retry-политика); polling-цикл в worker; `inbound_notifications` с
дедупликацией; DeleteNotification строго после commit; классификация типов
уведомлений, включая **[РЕШЕНИЯ]**: группы `@g.us` → ignored (чат не
создаётся), стикеры → message `IGNORED` без ответа; outbox с
идемпотентностью (`outbound_message_id`); связывание `outgoingAPIMessage`
с нашими отправками; **DRY_RUN** (отправка логируется, не выполняется);
мониторинг backlog и ошибок polling в `system_events`.

**DoD:** тесты: повторное уведомление не создаёт второй записи/обработки;
все типы уведомлений классифицируются; группа/стикер не порождают ответ;
ретрай отправки не дублирует сообщение (UNIQUE outbound_message_id);
DRY_RUN не шлёт наружу ничего. Все вызовы GREEN-API — только против
моков/фикстур; реальный инстанс не трогается.

## ФАЗА 3 — Чат-менеджер (без AI)

**Скоуп:** модели chats/messages/chat_memory/tags/internal_notes; API списка
чатов (cursor-пагинация, фильтры, поиск) и открытого чата; отправка из
панели (через outbox); теги, заметки, «решено»; флаг `needs_attention` +
автоснятие [РЕШЕНИЕ]: при `operator_phone`-ответе и при открытии диалога
в панели; audit_log на все действия; двухпанельный UI чатов (desktop-first,
тёмная тема, клавиатурная навигация), различение source визуально.

**DoD:** тесты: пагинация не теряет и не дублирует чаты на границах курсора;
отправка из панели идемпотентна; открытие чата снимает needs_attention и
пишет аудит; unread_count корректен при гонке входящих. UI работает без
загрузки всего архива (lazy load).

## ФАЗА 4 — Режимы диалога

**Скоуп:** state machine `AUTO_AI / HUMAN / PAUSED_UNTIL / DISABLED`;
автопереключение при сообщении оператора из панели и с телефона
(+продление таймера по настройке); варианты паузы из SPEC §7; активный
планировщик возврата из PAUSED_UNTIL; `chat_mode_history`; глобальный
emergency switch (не меняет режимы отдельных чатов); UI переключателей
в чате и глобального рубильника.

**DoD:** тесты SPEC §17 «Режимы» полностью: таймер возвращает в AUTO_AI
сам; сообщения оператора переключают; DISABLED молчит всегда; emergency
switch глушит всё; каждая смена — в истории и аудите.

## ФАЗА 5 — База знаний и RAG

**Скоуп:** kb_documents (статусы, версии, valid_until, is_searchable, soft
delete), kb_chunks (семантический чанкинг CHUNK_TOKENS/CHUNK_OVERLAP,
embeddings в фоне, HNSW), kb_processing_log; поиск: язык → категория →
metadata-фильтр → similarity → top-k → порог → дедуп; **FAQ по трёхъязычной
политике [РЕШЕНИЕ]**: kb_faq со статусами ответов absent/machine/approved,
kb_faq_patterns (language, normalized_pattern), правило отдачи (machine —
никогда; нет approved на языке клиента → RAG+LLM), kb_faq_misses;
**экран проверки переводов** (ru рядом с черновиком, Утвердить/Правка/
Удалить, фильтры по статусу и языку, массовое утверждение запрещено);
UI базы знаний (вкладки FAQ/Документы/Категории, просмотр чанков,
переиндексация, лог обработки); импорт/экспорт FAQ XLSX;
**`make kb-import`** — идемпотентный импорт документов из
`взято из савви.md` в статусе draft + генерация machine-черновиков kk/en
(детали — docs/knowledge-base-import.md). Embeddings в тестах — фикстуры;
реальный OpenAI не вызывается.

**DoD:** тесты: отключённый/архивный/удалённый документ не попадает в поиск;
переиндексация идемпотентна (UNIQUE document_id+chunk_index); FAQ-матч
по kk-паттерну без approved_kk НЕ отдаёт русский ответ и пишет промах;
machine-ответ недостижим для выдачи ни одним путём кода; повторный
kb-import не дублирует документы. Таблица kb_faq после миграций пуста.

## ФАЗА 6 — OpenAI и деньги

**Скоуп:** context_builder по SPEC §8 (стабильный префикс, память, summary,
RAG-чанки в тегах, обрезка по MAX_INPUT_TOKENS с приоритетами); клиент
OpenAI (официальный async SDK, timeout, retry-классификация); guardrails-
классификатор до модели; валидация вывода; ai_calls с фактическим usage;
model_prices + fx_rates + конвертация; **атомарный резерв бюджета** по всем
скоупам + settle + чистка held-резервов; semantic_cache; debounce; per-chat
lock; глобальный semaphore; circuit breaker; полный pipeline SPEC §6 в
worker (24/7, working_hours выключены по умолчанию [РЕШЕНИЕ]); раздел
админки «Лимиты» с пересчётом токены→деньги; sandbox-тест промпта (§12.3).

**DoD:** тест гонки: 20 параллельных при лимите 4 → ровно 4 вызова (против
PostgreSQL); зависший held освобождается; расчёт стоимости сходится с ручным
(включая cached и reasoning); смена курса не переписывает историю; повторное
уведомление не вызывает OpenAI (сквозной тест инварианта 3); prompt
injection и нецелевые запросы из SPEC §17 — шаблоны, минимум токенов;
ответ сохраняется ДО отправки, ретрай отправки не генерирует заново.

## ФАЗА 7 — Медиа

**Скоуп:** голосовые (валидация типа/размера/длительности ДО транскрибации,
gpt-transcribe со словарём терминов из настроек, транскрипт в БД, файл под
retention); изображения (сжатие 1024–1280px в thread pool, лимиты, vision,
сохранение описания и повторное использование без пересылки картинки);
эвристики запрещённых типов (документы/карты/медснимки → человеку, в OpenAI
не отправлять); видео/GIF/документы → настраиваемый шаблон или оператор
(стикеры уже игнорируются с фазы 2); retention-планировщик; безопасные пути
(resolve + is_relative_to).

**DoD:** тесты: аудио длиннее лимита → шаблон, транскрибация не вызвана;
огромное изображение → сжатие/отказ; запрещённый тип → человеку, в OpenAI
не ушло; файл вне base-каталога недостижим; retention удаляет файл,
транскрипт остаётся.

## ФАЗА 8 — Аналитика и расходы

**Скоуп:** разделы «Расходы» (§12.5) и «Аналитика» (§12.7) целиком: графики
по дням, разбивки по типам вызовов и моделям, cache hit rate и экономия,
топ дорогих диалогов/клиентов, прогноз исчерпания бюджета, латентность по
этапам, процент автоматизации; **FAQ-промахи по языку [РЕШЕНИЕ]** (сколько
kk/en ушло в LLM без approved-ответа, топ тем — рабочий список переводов);
курсы валют с журналом; экспорт CSV/XLSX; «Обзор» (дашборд §12.1).

**DoD:** каждая цифра сверяема с ai_calls/messages запросом (тест на
согласованность агрегатов); экспорт открывается в Excel; фильтры не
вызывают OpenAI (инвариант 16); дашборд грузится без полного скана таблиц
(EXPLAIN в тесте производительности запросов — индексы используются).

## ФАЗА 9 — Эксплуатация

**Скоуп:** pg_backup.sh / pg_restore.sh + ротация + `make backup-verify`
(restore во временный контейнер); мониторинг диска/памяти/контейнеров/
глубины очереди/backlog GREEN-API; **алерты через WhatsApp** на
`settings.alert_phone` [РЕШЕНИЕ: Telegram не используется]: пороги бюджета
50/80/90/100% (alert_notifications, один раз на порог), circuit breaker,
ошибки polling, диск >85%, падение healthcheck worker'а; страница «Система»
(§12.9): статусы GREEN-API/OpenAI, маскированный токен, очередь, последний
бэкап, диск/память, «Проверить подключение»; раздел «Учётная запись и
журнал» (§12.8); ротация логов; финальные конфиги deploy/nginx.

**DoD:** тесты: алерт на порог уходит один раз за период; failed-алерт
ретраится; restore реально восстанавливает данные (интеграционный тест
дампа); маскирование секретов в UI и логах (grep-тест); алерт-отправка
не порождает AI-обработку.

## ФАЗА 10 — Приёмка

**Скоуп:** полный прогон всех тестов; eval-набор (ru / kk / en / смешанная
казахско-русская речь; FAQ; сложные вопросы; нецелевые; обход; отсутствующая
информация; голосовые с названиями центра и секций) + **[РЕШЕНИЕ]
обязательные кейсы:** казахский вопрос при отсутствии approved_kk → ответ
на казахском через LLM, а не по-русски из FAQ; скрипт прогона + отчёт с
процентом прохождения и стоимостью; нагрузочная проверка 5 и 30 параллельных
чатов (очередь растёт, сервер жив, лимит параллельных вызовов держится);
полный dry-run прогон; чеклист прод-деплоя по docs/deployment.md §7;
финальный отчёт владельцу.

**DoD:** eval-отчёт приложен с цифрами; нагрузочный отчёт приложен;
чеклист деплоя пройден по пунктам на стейдже (локально/DRY_RUN);
список известных ограничений записан.
