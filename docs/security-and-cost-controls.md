# Безопасность и контроль расходов

Статус: ФАЗА 0. Дополняет SPEC §§2, 9, 10, 14. Здесь: модель угроз, формулы
контроля расходов, схема аутентификации, политика логирования и retention.

---

## 1. Модель угроз

Актив, который защищаем: деньги на OpenAI-счёте, ключи (OpenAI, GREEN-API),
переписка клиентов (PII), доступ к админке, целостность соседних проектов
на VPS.

### 1.1 Кто атакует и как

**A. Любой человек с WhatsApp (анонимный, неаутентифицируемый).**
Самая широкая поверхность: боту может написать кто угодно.

| Атака | Контроль |
|---|---|
| Prompt injection («игнорируй инструкции», «покажи промпт», «ты теперь…») | классификатор до модели (эвристики + микро-вызов); system-инструкция неизменяема; сообщение клиента и RAG-чанки размечены как данные; валидация вывода (нет фрагментов промпта, нет ссылок вне allowlist) |
| Нецелевое использование (код, эссе, экзамены) | тематический классификатор → шаблон, 0 токенов; `MAX_OUTPUT_TOKENS=350` делает бота бесполезным как генератор текстов |
| Cost bombing: флуд сообщениями | rate limit 5/мин, 30/час на номер; debounce склеивает очереди; `user_day` лимит 50 ₸ |
| Cost bombing: длинные аудио | `MAX_AUDIO_SECONDS=120`, проверка ДО транскрибации, шаблонный отказ |
| Cost bombing: картинки | `MAX_IMAGES_PER_DIALOG=3`, сжатие до 1024–1280 px, повторно картинка в модель не уходит (используется сохранённое описание) |
| Спам одинаковыми сообщениями | спам-фильтр: 5 одинаковых подряд → игнор (порог в настройках) |
| Выуживание данных других клиентов | память и кэш строго per-chat; в контекст попадают только чанки KB и текущий чат |
| Фото удостоверения/карты/медснимка БЕЗ подписи | **остаточный риск, принят осознанно.** Локальные бесплатные сигналы: ключевые слова подписи (ru/kk/en), номер карты/длинные цифры в подписи, «карточное» соотношение сторон. Фото без подписи распознать как документ до отправки невозможно (для классификации надо отправить), поэтому `vision_enabled=false` по умолчанию, а OCR вне скоупа фазы 7 (нет системных бинарей на VPS). Документы как тип файла не читаются вообще |
| Stored XSS через «фото», которое на деле SVG/HTML | на диск пишется НАШ перекодированный JPEG, отдача — с фиксированным Content-Type и `Content-Disposition: attachment` |
| SSRF через downloadUrl из недоверенного payload | https-only, allowlist хостов провайдера, запрет редиректов, отказ на приватные адреса после DNS; воркер живёт в одной сети с postgres/redis |
| Утечка GPS/устройства из EXIF | EXIF применяется (ориентация) и вырезается ДО записи на диск и до отправки в модель |
| Стикеры/видео/GIF как мусорный трафик | стикеры — полный игнор без ответа [РЕШЕНИЕ]; видео/GIF/документы в OpenAI не идут |
| Групповые чаты как обход лимитов | группы полностью игнорируются, чат не создаётся [РЕШЕНИЕ] |

**B. Интернет-сканер / целевой атакующий на `bot.mmedet.kz`.**

| Атака | Контроль |
|---|---|
| Брутфорс логина | rate limit по номеру и IP; прогрессивный lockout; одинаковый ответ для «нет номера»/«неверный пароль»; TOTP обязателен |
| Кража сессии через XSS | токен только в HttpOnly+Secure cookie; CSP без unsafe-inline; никакого localStorage; экранирование текстов чатов при выводе |
| CSRF | SameSite + CSRF-токен на мутирующие запросы + проверка Origin |
| Перебор/сканирование API | deny by default: каждый роут кроме `/healthz` требует сессию; автоматический тест обхода всех роутов |
| Утечка через ответы API | явные response-модели; никогда не отдаются `password_hash`, `totp_secret_encrypted`, `token_ref`, сырые payload'ы |

**C. Компрометация ключей.**

| Риск | Контроль |
|---|---|
| Секрет в git/логах/бандле | секреты только в `.env` (права 600); gitleaks в pre-commit и CI; греп собранного dist; маскировка в UI (`••••1234`) |
| Утечка OpenAI-ключа | отдельный OpenAI Project только под бота с hard spend limit (~4000 ₸/мес) — потолок ущерба даже при полной компрометации |
| Утечка GREEN-API токена | токен в `.env` (`token_ref` в БД); ротация через панель GREEN-API |

**D. Недоверенный вход от провайдера.** Payload GREEN-API — внешние данные:
валидация pydantic-схемой с лимитом размера, `media_ref` строится через
`Path.resolve()` + `is_relative_to(base)`, имена файлов провайдера не
используются как пути.

**E. Соседство на VPS.** Наши БД/Redis living в изолированной internal-сети,
портов на 0.0.0.0 нет; шлюз видит только frontend. Существующие проекты не
трогаем (SPEC инвариант 15).

**F. Supply chain.** Лок-файлы с хэшами; `pip-audit`, `bandit`, `npm audit`,
Trivy в CI; базовые образы запинены по digest.

### 1.2 Что сознательно НЕ защищаем

- DDoS уровня инфраструктуры — вне скоупа (VPS, нет CDN/WAF); частично
  гасится лимитами и тем, что вход только через WhatsApp/GREEN-API.
- Физический доступ к VPS и компрометация root — вне скоупа приложения;
  рекомендация владельцу: отключить парольный SSH в пользу ключей
  (аудит показал `PasswordAuthentication yes`).

## 2. Контроль расходов

### 2.1 Уровни защиты (от дешёвых к дорогим)

```
0 ₸  emergency switch / режим чата / группы / стикеры / rate limit / спам-фильтр
0 ₸  guardrails-классификатор (эвристики) → шаблон
0 ₸  прямой FAQ-матч (approved-ответ на языке клиента)
0 ₸  semantic cache hit
~0 ₸ микро-вызовы: классификатор темы/языка (reasoning none, max 10 токенов)
 $   атомарный резерв бюджета → транскрибация/vision/RAG/чат-вызов
```

### 2.2 Формулы

Оценка для резерва (верхняя граница):

```
estimate_usd = MAX_INPUT_TOKENS/1e6 × P(input)
             + MAX_OUTPUT_TOKENS/1e6 × P(output)
             + audio_minutes × P(audio)          # если есть голосовое
             + embed_tokens/1e6 × P(embedding)   # запрос в RAG
```

Фактическая стоимость (по usage из ответа API, не по оценке):

```
cost_usd = (input_tokens − cached_input_tokens)/1e6 × P(input)
         + cached_input_tokens/1e6 × P(cached_input)      # = 10% от input
         + (output_tokens + reasoning_tokens)/1e6 × P(output)
         + audio_seconds/60 × P(audio)
cost_kzt = cost_usd × rate(USD/KZT на момент вызова)      # фиксируется в ai_calls
```

Cache write = 1.25× input-ставки → стабильность блоков 1–2 контекста
(SPEC §8) обязательна, иначе кэш дороже его отсутствия.

### 2.3 Атомарный резерв

Решение принимает PostgreSQL тем же UPDATE, который пишет (SPEC §9.2):

```sql
UPDATE budget_ledger
   SET reserved_usd = reserved_usd + :estimate
 WHERE scope = :scope AND scope_key = :key AND period_start = :ps
   AND reserved_usd + spent_usd + :estimate <= limit_usd
RETURNING id;
```

Порядок: резерв по ВСЕМ скоупам (`global_day`, `global_month`, `chat:<id>`,
`user_day:<phone>`) в одной транзакции; отказ любого → освободить взятые →
`BLOCKED_BY_LIMIT` → шаблонный ответ без модели. После ответа — settle одним
UPDATE, идемпотентно по `(correlation_id, ledger_id)`. Планировщик
освобождает `held`-резервы старше N минут (дефолт 10).

Обязательный тест: 20 параллельных запросов при лимите на 4 → ровно 4 вызова,
`spent + reserved ≤ limit` всегда; против настоящего PostgreSQL.

### 2.4 Лимиты (дефолты из SPEC §9.3, все правятся в админке)

Дневной бюджет 300 ₸, месячный 3000 ₸, диалог 20 ₸, пользователь/день 50 ₸,
`MAX_INPUT_TOKENS=12000`, `MAX_OUTPUT_TOKENS=350`, остальное — SPEC §9.3.
Рядом с каждым полем в админке — пересчёт в деньги при текущей модели и курсе.

### 2.5 Алерты о бюджете **[РЕШЕНИЕ: WhatsApp, не Telegram]**

Пороги 50/80/90/100% дневного и месячного бюджета. Канал — WhatsApp-сообщение
через GREEN-API на `settings.alert_phone`. Дедупликация — `alert_notifications`
(`UNIQUE (kind, event_key, period_key)`): один порог = одно сообщение за период.

Ограничение канала: о падении самого GREEN-API алерт через GREEN-API не
доставить. Компенсации: событие в `system_events` + страница «Система»;
недоставленный алерт (`status=failed`) ретраится после восстановления канала.

### 2.6 Второй, независимый уровень

Отдельный OpenAI Project только под бота, hard spend limit ~4000 ₸/мес в
USD-эквиваленте (выше внутреннего месячного лимита 3000 ₸). Инструкция
владельцу — в README. Баг приложения не может пробить лимит OpenAI; лимит
OpenAI не заменяет внутренний учёт.

## 3. Аутентификация (сжатая схема; полностью — SPEC §10)

- Одна учётка. Логин = телефон E.164 + пароль (argon2id, ≥12 симв.) +
  обязательный TOTP. Опция: OTP через WhatsApp (GREEN-API) вместо TOTP —
  реализуется, но дефолт TOTP.
- Учётка создаётся `make create-admin` (пароль из stdin); регистрации нет;
  второй активный админ = приложение не стартует.
- 8 одноразовых recovery-кодов, в БД — хэши.
- Сессии серверные: в cookie `secrets.token_urlsafe(32)`, в БД — хэш.
  HttpOnly, Secure, SameSite=Lax, узкий Path. Idle + absolute timeout.
  Смена пароля ревокает остальные сессии.
- «Пароль принят, ждём TOTP» — не сессия: промежуточное состояние не даёт
  доступа ни к одному API (обязательный тест).
- Rate limit на `/auth/login` по номеру и IP; прогрессивный lockout;
  все попытки — в audit_log.
- Каждый роут кроме `/healthz` — `require_admin()`; автоматический тест
  обходит `app.routes` и требует 401 без сессии.

## 4. Логирование

Структурированный JSON (structlog), `correlation_id` в каждой записи.

**Никогда не логируются:** токены, ключи, заголовки авторизации, пароли,
тексты сообщений клиентов, промпты с PII, телефоны в открытом виде
(маскировать `+7701***1555`).

**Логируются:** id (chat_id, message_id, correlation_id), типы событий,
состояния state machine, метрики (токены, стоимость, latency по этапам
receive → queue → transcription → RAG → OpenAI → send), коды ошибок.

Уровни хранения:
- контейнерные логи: json-file driver, ротация (max-size/max-file в compose);
- `system_events` (БД): события для страницы статуса, 90 дней;
- `audit_log` (БД): действия администратора и системы над сущностями,
  365 дней, без текстов клиентов и секретов.

## 5. Retention policy

| Данные | Срок | Механизм |
|---|---|---|
| Медиа-файлы (голос, фото) | 7 дней (настройка) | планировщик удаляет файлы; транскрипт/описание остаются в БД |
| `inbound_notifications.raw_payload` | 30 дней после обработки | планировщик обнуляет поле, строка-дедупликатор остаётся |
| Сообщения и чаты | бессрочно | владельцу нужна история; настройка авто-чистки может быть добавлена позже без изменения схемы |
| `ai_calls` | бессрочно | финансовая отчётность; PII не содержит |
| `semantic_cache` | TTL (настройка) + инвалидация по kb_version | планировщик |
| Истёкшие сессии | 30 дней после expiry | планировщик |
| `system_events` | 90 дней | планировщик |
| `kb_faq_misses` | 180 дней | планировщик |
| `audit_log` | 365 дней | планировщик |
| Следы отправки (`wa_outbox`) и завершённые медиа-задачи | 30 дней (настройка) | планировщик; неотправленные строки не трогаются |
| `download_url` медиа-задачи (ссылка провайдера на файл клиента) | сразу после завершения задачи | планировщик обнуляет поле |
| Истёкшие login-челленджи | 1 день | планировщик |
| Доставленные оповещения | 90 дней | планировщик |
| Бэкапы БД | 7 дневных + 4 недельных + 3 месячных, на сервере [РЕШЕНИЕ: offsite нет] | systemd-таймер/cron + ротация, см. deployment.md |

Реализация — `backend/app/services/retention.py`, цикл воркера раз в 6
часов; все сроки правятся в разделе «Лимиты». Удаление идёт партиями по
первичному ключу и опирается на индексы миграции 0009 — иначе ночная
уборка держала бы блокировки и тормозила ответы клиентам.

Маскирование PII: телефоны маскируются в логах и алертах; в БД хранятся
полностью (нужны для работы), доступ к БД — только изнутри internal-сети.
Трассировки исключений печатаются БЕЗ локальных переменных
(`show_locals=False` в `observability/logging.py`): по умолчанию structlog
выводит локальные переменные каждого кадра, а это токен провайдера и текст
клиента целиком в контейнерном логе. Закрыто тестом
`tests/unit/test_logging.py`.

## 6. Прикладная безопасность — чеклист каждого PR

Полный список — SPEC §14.2. Ключевое, что проверяется ревью и CI:
параметризованный SQL; `secrets`, не `random`; `subprocess` списком без
`shell=True`; `timeout=` на каждом исходящем запросе; pydantic-валидация
каждого входа с лимитом размера; CORS — точный allowlist
(`https://bot.mmedet.kz`), падение при пустом; security-заголовки на всех
ответах (HSTS, nosniff, CSP без unsafe-inline, frame-ancestors 'none');
редиректы только на относительные пути; фронт без dangerouslySetInnerHTML
на данных чатов; Docker non-root, digest-pinned, cap_drop ALL, лимиты
памяти/CPU; gitleaks, pip-audit, bandit, ruff, mypy, npm audit в CI.

Если секрет попал в git: сначала отозвать/перевыпустить, потом чистить
историю, и сказать владельцу прямо.
