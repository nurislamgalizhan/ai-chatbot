# Архитектура системы

Статус: ФАЗА 0 (проектирование). Источник истины — `SPEC.md`. Решения владельца,
принятые после SPEC, помечены как **[РЕШЕНИЕ]** и имеют приоритет над текстом SPEC
там, где они его уточняют.

---

## 1. Обзор

WhatsApp AI-бот с админ-панелью: принимает сообщения клиентов через GREEN-API,
отвечает на основе утверждённой базы знаний (прямые FAQ + RAG на pgvector +
OpenAI), передаёт диалог человеку, когда нужно, и даёт владельцу полный контроль
над расходами.

**[РЕШЕНИЕ] Система строится как white-label.** В коде нет ни одного упоминания
конкретной организации: название («СУЦ Меркурий Медет»), инструкция агента,
база знаний, номер для алертов, часовой пояс, домен админки — всё это данные
(таблицы `settings`, `agent_instructions`, `kb_*`) или конфигурация
(`.env`, конфиг деплоя). Модель развёртывания — **single-tenant**: одна
инсталляция = одна компания. Для второй компании поднимается вторая копия
compose-проекта со своей БД и своим `.env`. Мультитенантность в одной БД
сознательно не проектируется (см. SPEC §10 о неиспользуемых системах — это
код, который никто не тестирует).

Первая инсталляция — СУЦ «Меркурий Медет» (специализированный учебный центр:
подготовка охранников, спорткомплекс, гостиница, соревнования). Бот
представляется «СУЦ Меркурий Медет».

              └─────────────┬──────────────┘
                            │ docker-сеть (edge)
              ┌─────────────▼──────────────┐

              │  /api/* → backend:8000     │
              └─────────────┬──────────────┘
                            │ внутренняя docker-сеть (internal)
        ┌───────────────────┼────────────────────┐
        │                   │                    │
┌───────▼───────┐   ┌───────▼───────┐    ┌───────▼───────┐
│    backend    │   │    worker     │    │     redis     │

└───────┬───────┘   └───────┬───────┘    └───────────────┘
        │                   │
        └─────────┬─────────┘
          ┌───────▼───────┐         GREEN-API ◄── worker (polling, исходящий)

Наружу не публикуется ни один порт (SPEC инвариант 13). Админка доступна
только через существующий шлюз. Все соединения с GREEN-API и OpenAI —
исходящие; вебхуков нет, публичных входов нет.

### 2.1 backend (API-процесс)

Отвечает **только** за админ-панель: аутентификация, чаты (чтение/отправка
из панели), база знаний, настройки, аналитика, система. Никогда не вызывает
OpenAI для рендера истории (SPEC инвариант 16). Единственный
неаутентифицированный роут — `/healthz`.

### 2.2 worker (отдельный процесс, тот же Docker-образ)

Вся асинхронная работа. Внутри одного процесса:

- **Poller** — цикл `ReceiveNotification` → сохранение в
  `inbound_notifications` → `DeleteNotification` только после commit →
  классификация типа уведомления.
- **Dispatcher** — выборка чатов с сообщениями `state=QUEUED`, у которых
  истекло debounce-окно; на каждый чат — задача под per-chat Redis-lock.
- **AI-pipeline** — предохранители → FAQ → semantic cache → резерв бюджета →
  медиа → RAG → сборка контекста → OpenAI → сохранение → отправка (раздел 4).
- **Scheduler** (периодические задачи):
  - возврат чатов из `PAUSED_UNTIL` в `AUTO_AI` (активный, не «ленивый»);
  - освобождение зависших `held`-резервов бюджета;
  - автоудаление медиа по retention;
  - очистка `raw_payload` старых уведомлений, истёкших сессий, semantic cache;
  - пересборка summary диалогов по порогу;
  - проверка порогов бюджета и рассылка алертов;
  - мониторинг: место на диске, глубина очереди, ошибки polling.
- **Alert dispatcher** — см. раздел 6.

Worker запускается в **одной реплике**. Глобальный лимит параллельных
AI-задач (`MAX_CONCURRENT_AI_REQUESTS`, дефолт 8) — процессный semaphore;
per-chat порядок — Redis `SET NX + TTL`. Масштабирование на несколько реплик
не проектируется (2 vCPU; при ~100–300 сообщениях в день не нужно).

### 2.3 Очередь: PostgreSQL, а не брокер

Очередь задач — это state machine сообщений в PostgreSQL
(`RECEIVED → QUEUED → PROCESSING → GENERATED → SENT / FAILED_* / IGNORED / ...`).
Redis используется только для координации: locks, debounce, rate limits.

Обоснование: durability из коробки (перезапуск контейнера посреди обработки
не теряет сообщение — обязательный тест SPEC §17), нет лишнего компонента на
слабом VPS, дедупликация и идемпотентность и так живут в PostgreSQL. При
нашем объёме (десятки-сотни сообщений в день, пик 30 параллельных чатов)
опрос БД раз в ~1 секунду — пренебрежимая нагрузка.

### 2.4 frontend

React + TypeScript + Vite, собирается в статику, отдаётся контейнером
nginx:alpine (тот же паттерн, что у существующих сайтов VPS). `/api/*` и
опрос обновлений проксируются на backend. Токены — только в HttpOnly cookie,
localStorage не используется.

### 2.5 Provider-adapter (транспорт WhatsApp)

```
WhatsAppProvider (ABC)
 ├── GreenApiProvider   # сейчас; один инстанс [РЕШЕНИЕ], оплачен, лимиты
 │                      # владелец контролирует в панели GREEN-API
 └── MetaWabaProvider   # потенциально; без переписывания чатов/RAG/админки
```

Интерфейс: `poll_notifications()`, `delete_notification(receipt_id)`,
`send_text(chat_id, text, idempotency_key)`, `send_file(...)`,
`set_typing(chat_id)`, `get_instance_state()`.

Бизнес-логика не знает про GREEN-API. Мультиинстансность в UI не делается
(таблица `whatsapp_instances` остаётся — это дёшево и держит схему готовой),
активный инстанс один.

## 3. Классификация входящих уведомлений

| Тип уведомления | Действие |
|---|---|
| `incomingMessageReceived`, личный чат | создать/обновить chat → message `QUEUED` → pipeline |
| `incomingMessageReceived`, **групповой чат** (`@g.us`) | **[РЕШЕНИЕ]** сохранить в `inbound_notifications` со статусом `ignored`. Chat не создаётся, message не пишется, AI не запускается, бот в группы не пишет ничего |
| `incomingMessageReceived`, **стикер** | **[РЕШЕНИЕ]** message сохраняется (`media_type=sticker`, `state=IGNORED`), AI не вызывается, шаблон-ответ НЕ отправляется — полный игнор |
| `outgoingMessageReceived` (человек ответил с телефона) | сохранить как `operator_phone`, активировать/продлить паузу AI, снять флаг «требует внимания», AI не запускать |
| `outgoingAPIMessageReceived` (наша отправка) | связать по `outbound_message_id`, обновить статус; AI не запускать |
| статусы доставки / звонки / события инстанса | system-событие, стоп |

AI запускается ТОЛЬКО на `incomingMessageReceived` личного чата
(SPEC инвариант 7).

## 4. Pipeline обработки сообщения

Как в SPEC §6, с уточнениями по решениям владельца:

```
worker (per-chat lock, debounce 2–4 c)
 ├─ 7.1  emergency switch выключен? → стоп
 ├─ 7.2  режим чата = AUTO_AI? → иначе стоп
 ├─ 7.3  рабочее время: [РЕШЕНИЕ] бот отвечает 24/7. Проверка остаётся
 │       в коде как настройка (working_hours в settings), по умолчанию
 │       ВЫКЛЮЧЕНА — для переиспользования кода другими компаниями
 ├─ 7.4  rate limit пользователя (msg/min, msg/hour)
 ├─ 7.5  спам-фильтр (5 одинаковых сообщений подряд — из настроек)
 ├─ 7.6  лимиты медиа (изображений в диалоге, длины аудио, размера файла)
 ├─ 7.7  guardrails: prompt injection / нецелевая тема → шаблон без LLM
 ├─ 7.8  прямой FAQ-матч (мультиязычный, см. раздел 5) → 0 токенов → отправка
 ├─ 7.9  semantic cache hit → 0 токенов → отправка
 ├─ 7.10 атомарный резерв бюджета (global_day, global_month, chat, user_day)
 ├─ 8    медиа: voice → транскрибация; image → сжатие → vision
 │        РЕАЛИЗАЦИЯ (фаза 7): медиа обрабатывается ОТДЕЛЬНЫМ циклом
 │        воркера ДО шагов 7.7–7.10, потому что FAQ и кэш требуют текста,
 │        которого до транскрибации ещё нет. Порядок в медиа-цикле:
 │        emergency → режим чата → отсечка возраста → лимиты медиа →
 │        резерв бюджета → платный вызов. Результат пишется в
 │        messages.transcript, сообщение остаётся QUEUED, и обычный
 │        пайплайн отвечает на него как на текст (при этом чат с
 │        незавершённым медиа не выбирается — порядок сообщений внутри
 │        чата сохраняется). Документы/видео/GIF в OpenAI не идут никогда.
 ├─ 9    RAG: язык+категория → metadata-фильтр → similarity → top-k → порог
 ├─ 10   сборка контекста (SPEC §8) → вызов OpenAI
 ├─ 11   ai_calls с фактическим usage; settle резерва
 ├─ 12   message(state=GENERATED) с текстом — ДО отправки
 ├─ 13   provider.send() с outbound_message_id (идемпотентность)
 └─ 14   state=SENT; обновить chat, стоимость, аналитику
```

Ошибки: retryable → backoff+jitter, максимум 3; ошибка отправки повторяет
только шаг 13; серия ошибок → circuit breaker + алерт (WhatsApp, раздел 6).
`correlation_id` живёт от шага 1 до конца.

### 4.1 Пауза перед ответом (debounce)

Настройка «Задержка перед ответом» (`debounce_seconds`, 0–60 с, дефолт 3)
задаёт, сколько конвейер ждёт после ПОСЛЕДНЕГО сообщения чата, прежде чем
взять его в работу. Всё накопившееся склеивается в один вопрос к модели и
оплачивается как один вызов.

Окно скользящее, поэтому у него есть жёсткий потолок 120 секунд
(`_MAX_DEBOUNCE_WAIT`): иначе клиент, пишущий чаще, чем длится окно, не
получил бы ответа никогда. Чат созревает, если выполнено любое из трёх:
тишина длиннее окна; самое старое сообщение ждёт дольше потолка; в чате
есть сообщение, которое всё равно не пойдёт в модель (файл, геолокация,
карточка контакта) — такому ждать нечего, его ждёт менеджер.

Склейка меняет три вещи ниже по конвейеру: одинаковые реплики внутри
батча схлопываются в одну строку, батч считается ОДНОЙ попыткой для
спам-фильтра, а слишком длинная склейка обрезается до последних сообщений
вместо отказа «напишите короче». Если склеенный текст не совпал ни с одной
формулировкой FAQ, каждая реплика проверяется по FAQ отдельно: когда
совпали все, ответ остаётся бесплатным.

## 5. Языки и FAQ **[РЕШЕНИЕ — ключевая политика]**

Русский — единственный источник истины базы знаний. Любая правка начинается
с ru-версии.

**Матчинг FAQ мультиязычный с первого дня.** Паттерны вопросов хранятся с
указанием языка (`kb_faq_patterns.language`); для каждой FAQ-записи
обязательны паттерны ru и kk, для части — en.

**Ответы имеют статус на каждый язык:** `absent | machine | approved`.
`machine` (машинный черновик) клиенту не отдаётся **ни при каких условиях** —
он виден только в админке на экране проверки переводов.

**Правило отдачи ответа:**

```
язык клиента = kk, FAQ-паттерн совпал:
  answer_kk_status == approved → отдать answer_kk (0 токенов)
  иначе → записать «FAQ-промах по языку» и провалиться в RAG+LLM,
          который ответит на языке клиента
```

Русский текст на казахский вопрос НЕ подставляется никогда — потратить
~0.25 ₸ на LLM лучше, чем ответить не на языке клиента. То же правило для
en и для смешанной казахско-русской речи.

FAQ-промахи по языку — отдельная метрика аналитики (сколько kk/en-запросов
не нашли approved-ответа и ушли в LLM, топ тем) — это рабочий список того,
что переводить следующим.

В FAQ попадает только то, что меняется реже раза в год (адрес, геолокация,
телефоны, график, как добраться, парковка, вызов администратора,
приветствие, прощание) — ожидаемо 8–10 записей. Цены, наличие мест, состав
секций, условия аренды, акции — только RAG+LLM (SPEC §11).

Определение языка сообщения: эвристики (казахские буквы ә ғ қ ң ө ұ ү һ і,
латиница для en) → при неуверенности короткий классифицирующий вызов
(`reasoning: none`, `max_output_tokens: 10`). Язык кэшируется в
`chat_memory.language` и уточняется по ходу диалога.

## 6. Эскалация и алерты

### 6.1 «Требует внимания» вместо сущности «Заявка» **[РЕШЕНИЕ]**

Отдельной таблицы заявок нет. Когда бот собрал данные для заявки или не
может помочь — чат получает флаг `needs_attention` (+причина). Флаг виден
в списке чатов («требует внимания») и снимается автоматически, когда:

- менеджер ответил клиенту со своего телефона напрямую в WhatsApp
  (пришло `outgoingMessageReceived`), ЛИБО
- администратор открыл этот диалог в админ-панели.

Снятие флага пишется в аудит с причиной (`operator_phone_reply` /
`panel_opened` / `manual`).

Кто СТАВИТ флаг (фаза 10 закрыла пробел): модель инструментов не имеет
и поднять флаг не может, а FAQ-ответ «передаю администратору» вообще не
доходит до модели. Поэтому конвейер сам распознаёт по словам клиента
(`services/escalation.py`, ru/kk/en, совпадение по префиксам слов)
просьбу позвать человека и запрос на бронь/запись — и ставит
`needs_attention` (причина `handoff`) плюс `handoff_required` в памяти
чата, не отменяя сам ответ. Остальные источники флага: устаревшее
сообщение, файл/медиа, «нет данных», отказ бюджета, ошибка обработки.

### 6.2 Алерты — через WhatsApp, Telegram не используется **[РЕШЕНИЕ]**

Все упоминания «Telegram-алертов» в SPEC заменяются на: **отправка
WhatsApp-сообщения через тот же GREEN-API-инстанс на номер, указанный в
админ-панели** (`settings.alert_phone`). Поводы: пороги бюджета
50/80/90/100% (один раз на порог на период), circuit breaker, рост backlog
уведомлений, ошибки polling, диск/память, падение healthcheck.

Честное ограничение: если недоступен сам GREEN-API, алерт о его падении
доставить нечем. Компенсация: все события пишутся в `system_events` и видны
на странице «Система»; алерт ретраится с backoff до восстановления канала.
Алерт-сообщения — исходящие API-сообщения, AI на них не запускается по
определению (инвариант 7), петля исключена.

## 7. Границы ответственности

| Забота | Где живёт |
|---|---|
| Полная история чата | PostgreSQL; в модель НИКОГДА не уходит целиком (инвариант 1) |
| Контекст для модели | `ai/context_builder` — только по схеме SPEC §8 |
| Деньги | `budget_ledger` в PostgreSQL, атомарный UPDATE (SPEC §9.2); никакой логики лимитов в Python-if |
| Дедупликация | UNIQUE-constraints в PostgreSQL, не память процесса |
| Секреты | только `.env`; в БД — `token_ref`, не токены |
| Права | одна учётка, `require_admin()` на всё кроме `/healthz` |
| Транспорт WhatsApp | `whatsapp/` за интерфейсом `WhatsAppProvider` |
| Бизнес-логика | `services/` — без HTTP и без SDK |
| Специфика компании | БД + `.env`; в коде — ноль упоминаний |

## 8. Решения владельца, зафиксированные в этой фазе

1. Организация — СУЦ «Меркурий Медет»; бот представляется именно так.
2. Заявка = флаг «требует внимания», автоснятие (см. 6.1).
3. Бот отвечает 24/7; механизм рабочих часов в коде есть, но выключен.
4. Группы: не читаем, не пишем. Стикеры: полный игнор без ответа.
5. Языковая политика FAQ — раздел 5 (ru — источник истины; статусы
   absent/machine/approved; машинные черновики клиенту никогда; промахи
   по языку — в аналитику; массовое утверждение переводов запрещено).
6. Инфраструктура: nginx только в Docker (app-gateway-nginx), certbot на
   хосте, Ubuntu 24.04 — детали в `docs/deployment.md`.
7. Бэкапы хранятся на самом сервере, offsite-хранилища нет.
8. GREEN-API: один инстанс, оплачен на год, лимиты — на стороне панели
   GREEN-API.
9. Telegram нигде не используется; алерты — WhatsApp на номер из админки.
10. Код переиспользуем для других компаний (white-label, single-tenant).
