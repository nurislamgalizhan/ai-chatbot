# CLAUDE.md — рабочие правила проекта

Источник истины — `SPEC.md`. Этот файл — сжатая шпаргалка + решения
владельца, принятые после SPEC. При конфликте: решения владельца (§4 ниже) >
SPEC > этот файл.

## 1. Режим работы

- Фазы и гейты жёсткие (SPEC §3): код фазы N+1 не пишется до закрытия гейта N.
  Текущее состояние: **все фазы 0–10 реализованы; гейт фазы 10 «Приёмка»
  ждёт подтверждения владельца. Дальше — только ручные шаги владельца по
  чеклисту деплоя (docs/deployment.md §7) и живой eval с ключом OpenAI.**
- Каждая фаза = отчёт (что сделано, файлы, тесты и как запустить, решения,
  вопросы) → стоп, ждать подтверждения владельца.
- Никаких заглушек как результата. Никаких молчаливых действий с реальной
  инфраструктурой: VPS, Nginx-шлюз, прод-БД, реальные ключи GREEN-API/OpenAI,
  отправка реальным номерам — только скрипты/конфиги + план на согласование.
- Не расширять скоуп. Видишь ошибку в требованиях — скажи прямо, не выполняй
  молча.
- **Языки:** код, комментарии, идентификаторы, коммиты — английский.
  `docs/`, README, UI-тексты, сообщения клиентам, общение с владельцем —
  русский.

## 2. Инварианты (нарушение = критический баг; полный список — SPEC §2)

1. В OpenAI никогда не уходит вся история переписки и никогда — вся база
   знаний. Только: system → память → summary ≤300 ток. → 6–10 последних
   сообщений → 3–5 чанков → вопрос.
2. Дедупликация — UNIQUE-констрейнты в PostgreSQL, не память процесса.
   Один `(instance_id, message_id)` = максимум один вызов OpenAI.
3. Текст ответа сохраняется в БД ДО отправки; ретрай отправки не генерирует
   заново.
4. Бюджет резервируется атомарным UPDATE в PostgreSQL до платного вызова
   (SPEC §9.2). Проверка лимита в Python — не лимит.
5. AI запускается ТОЛЬКО на `incomingMessageReceived`.
6. У модели нет tools с доступом к данным/файлам/сети. Сообщения клиента и
   RAG-чанки — данные, не инструкции.
7. Секреты только в `.env`. Порты БД/Redis/сервисов наружу не публикуются.
8. Все роуты кроме `/healthz` — за `require_admin()`; одна учётка, ролей нет.
9. PII и тексты клиентов не попадают в логи; телефоны маскируются.
10. Существующие проекты VPS (mmedet.kz, qr.bva.kz, шлюз, порты 80/443/22)
    не трогать.
11. Просмотр чатов в админке не вызывает OpenAI.
12. `DRY_RUN=true` — с фазы 2 и навсегда (режим приёмки).

## 3. Команды

`make up / down / logs / migrate / test / lint / backup / create-admin /
reset-admin-password / kb-import / seed-prices / backup-verify`.
Приёмка (фаза 10): `make eval` (офлайн, бесплатно), `make eval-live`
(реальная модель, деньги), `make load-test`, `make preflight`
(`python -m app.cli preflight --with-provider` — ещё и запросы к GREEN-API).
Все четыре работают внутри контейнера backend; eval и load-test создают
временную базу рядом с рабочей и удаляют её; отчёты — в `reports/`
(в git не попадают; эталонные прогоны приёмки — `docs/acceptance/`).
Тесты гонок — только против настоящего PostgreSQL. CI: ruff, mypy, bandit,
pip-audit, gitleaks, trivy, npm audit, тесты.

## 4. Решения владельца (2026-08-31, приоритет над текстом SPEC)

1. **White-label:** в коде ноль упоминаний конкретной компании; вся
   специфика — в `settings`/БД/env. Одна инсталляция = одна компания.
2. **Организация:** СУЦ «Меркурий Медет» — специализированный учебный центр
   (подготовка охранников) со спорткомплексом, гостиницей, соревнованиями.
   Бот представляется «СУЦ Меркурий Медет».
3. **Заявок как сущности нет:** флаг `chats.needs_attention`; снимается
   автоматически при ответе менеджера с телефона (`operator_phone`) или при
   открытии диалога в админке.
4. **Бот работает 24/7.** Механизм рабочих часов в коде есть, по умолчанию
   выключен.
5. **Группы WhatsApp:** не читаем и не пишем (чат не создаётся).
   **Стикеры:** полный игнор без ответа и без вызова модели.
6. **Языковая политика FAQ:** ru — источник истины; паттерны ru+kk
   обязательны; статусы ответов absent/machine/approved на каждый язык;
   machine-ответ клиенту НЕ отдаётся никогда; нет approved на языке клиента →
   RAG+LLM на языке клиента (русский не подставлять); FAQ-промахи по языку —
   метрика аналитики; утверждение переводов только по одной записи;
   в FAQ только факты, меняющиеся реже раза в год (8–10 записей).
7. **Алертов в Telegram нет.** Все алерты — WhatsApp через GREEN-API на
   номер из настроек (`alert_phone`).
8. **Бэкапы только на самом сервере** (offsite-хранилища нет — решение
   владельца, риск зафиксирован).
9. **GREEN-API:** один инстанс, оплачен; лимиты тарифа владелец контролирует
   в панели GREEN-API. Мультиинстансный UI не делаем.
10. **Импорт Savvi:** всё из `взято из савви.md` вводится в базу знаний как
    есть (draft), пробелы данных не блокируют; блоки отключаемы.
11. **Модель — `gpt-5.6-luna`** (подтверждено владельцем; совпадает с
    SPEC §9.1). Задаётся только через env/настройки, в коде не хардкодится.
12. **Сертификаты существующих доменов VPS** — зона ответственности
    владельца; в наших документах и задачах их нет.
13. **Тема админки — СВЕТЛАЯ, по образцу Савви** (решение владельца
    2026-09-01, отменяет пункт SPEC §12 об обязательной тёмной теме).
    UI/UX-паттерны брать из живых скриншотов `docs/ui-reference/img/` —
    перед любой UI-задачей открыть референс и повторить их решение.
    Палитра — только через CSS-токены в `:root` (тёмную тему можно
    добавить позже одним блоком переменных).

### Фаза 5: реализованные решения по базе знаний

- Индексация только в воркере, никогда в HTTP-запросе; черновики и архив
  не индексируются вообще (импорт 9 документов стоит 0 токенов).
- `machine`-перевод недостижим для выдачи: единственная точка извлечения
  ответа — `approved_answer()` в `services/kb_faq.py`.
- Промах по языку = совпал паттерн, но нет approved на языке клиента →
  `kb_faq_misses` (без текста клиента) → аналитика «что переводить».
- Массового утверждения переводов нет как эндпоинта — только по одной
  записи (`PATCH /api/kb/faq/{id}/answer`).
- Подсчёт токенов для чанкинга — оценочный (`ai/tokens.py`); точный
  токенизатор появится в фазе 6, где токены = деньги.

### Фаза 6: реализованные решения по деньгам и пайплайну

- **Отсечка возраста сообщений — 1 час** (решение владельца 2026-09-06;
  настройка `ai_max_message_age_minutes`): старше → `IGNORED` +
  `error_code="stale"` + `needs_attention`, отвечает менеджер.
- **Определение языка — порог**: kk только если казахских букв ≥5% от
  всех кириллических (имя «Айгерім» в русской фразе не переключает язык).
- Единственный шов платного конвейера — `generate_reply()` в
  `services/generation.py` (guardrails → FAQ → кэш → breaker → резерв →
  RAG → контекст → модель → цена). Sandbox и воркер зовут его же;
  ai_calls пишется на каждый ПЛАТНЫЙ вызов (sandbox — с `chat_id NULL`);
  бесплатные ответы (FAQ, кэш) возвращаются раньше, их след —
  `messages.answer_source` (фаза 8).
- Детерминированные ID: correlation = `chat:{id}:msg:{last_id}`, ответ =
  `uuid5(correlation)`; ретрай находит готовый GENERATED, а не платит
  второй раз. PROCESSING несёт lease в `next_attempt_at` — sweeper
  дочищает сирот (SPEC §17 «перезапуск посреди обработки»).
- Резерв бюджета: строго SQL SPEC §9.2; скоупы в каноническом порядке
  (без deadlock); резерв в отдельной короткой транзакции; суб-корреляция
  `{corr}:main:a{attempt}` — новая попытка = новый резерв, старый held
  снимает sweeper (15 мин). Лимиты в ₸, конверсия по курсу владельца;
  без курса/цен — fail closed (AI не тратит).
- Правка лимита в UI обновляет и УЖЕ открытые периоды ledger.
- Circuit breaker в Redis (общий для воркера и sandbox), half-open;
  проверяется после бесплатных путей и до резерва; заблокированные
  сообщения ждут в QUEUED без расхода retry_count.
- Semantic cache: механизм полный, но **выключен по умолчанию**
  (`semantic_cache_enabled=false`); kb_version — счётчик в settings,
  инкрементируется каждой мутацией БЗ. Не кэшируются: ПД, память чата,
  склейки, шаблоны, ответы без чанков.
- Summary-микровызов ОТЛОЖЕН (осознанно): context builder читает
  `chat_memory.summary_text`, но пока его никто не генерирует; память
  чата — только правила/regex.
- Цены моделей сидятся ТОЛЬКО командой `make seed-prices` (идемпотентна,
  не перезаписывает правки владельца); курс USD/KZT вводится вручную в
  «Лимитах», журналом. DRY_RUN ≠ бесплатно — зафиксировано в README и UI.

### Фаза 7: реализованные решения по медиа

- **Голосовые распознаются, фото — по умолчанию НЕТ**
  (`vision_enabled=false`): фото паспорта/карты без подписи невозможно
  отличить от фото зала, не отправив его в модель, а SPEC §13 это
  запрещает. Владелец включает осознанно в «Лимиты» → «Медиа».
- **Документы, видео, GIF не читаются никогда** — сразу человеку +
  бесплатный шаблон клиенту (не тишина). Стикеры игнорируются с фазы 2.
- Медиа обрабатывается отдельным циклом воркера ДО шагов FAQ/кэша
  (у них ещё нет текста); порядок: emergency → режим чата → отсечка
  возраста (1 час) → лимиты медиа → резерв → платный вызов. Отклонение
  от буквального порядка SPEC §6.7 зафиксировано в `docs/architecture.md`.
- **Барьер против двойной оплаты** — частичный UNIQUE
  `ai_calls (correlation_id, call_type)`: строка пишется ДО платного
  вызова, поэтому крах после оплаты не приводит ко второму списанию
  (ретрай отдаёт сообщение человеку с `already_charged`).
- Своя таблица `media_jobs` с лизом и СВОИМ счётчиком попыток: общий
  `messages.retry_count` съедал бы бюджет ретраев AI-пайплайна.
- Чат с незавершённым медиа не выбирается пайплайном — сохраняется
  порядок сообщений и не возникает горячего цикла воркера.
- Длительность аудио измеряется локально (mutagen) ДО платного вызова;
  цена — по секундам (одно целое и для резерва, и для факта).
- На диск пишется НАШ перекодированный JPEG без EXIF (приватность +
  защита от «фото», которое на деле SVG/HTML); отдача файла в панель —
  только через эндпоинт по паре id, `attachment`, фиксированный тип.
- Скачивание: https-only, allowlist хостов провайдера, без редиректов,
  отказ на приватные адреса (воркер в одной сети с БД и Redis).
- OCR из SPEC §13 вне скоупа: нет системных бинарей на VPS
  (компенсировано ключевыми словами подписи + vision по умолчанию off).
- Retention: файлы удаляются по `media_retention_days` (7),
  транскрипты и описания остаются; плюс сборка мусора по файловой
  системе — файлы, чей `media_ref` не закоммитился, иначе утекают.

### Правки 2026-09-11 (по прямым замечаниям владельца)

- **Переводы kk/en и триггерные формулировки генерирует ИИ**
  (`services/kb_ai.py`, кнопки «Перевести с русского» и «Подобрать
  формулировки» внутри записи). Автоматизирован НАБОР ТЕКСТА, но не
  решение: перевод сохраняется статусом `machine`, который
  `approved_answer()` не отдаёт клиенту; утверждение — по одной записи,
  массового эндпоинта по-прежнему нет. Оплата — через тот же атомарный
  резерв и `ai_calls`, цена показывается владельцу после генерации.
- **Шаблонные ответы удалены** (`DEFAULT_TEMPLATES`, `pick_template`,
  редактор на странице «Агент»). Отказы, передачу менеджеру и квитанции
  о файлах бот формулирует сам — `compose_service_reply()`. Текст
  клиента в модель при этом НЕ передаётся: модель получает нейтральное
  описание ситуации, поэтому попытка инъекции не доезжает до модели
  через вызванный ею же отказ. Осталась одна встроенная фраза — только
  на случай, когда модель недоступна (нет ключа, открыт breaker,
  исчерпан бюджет); во всех этих случаях диалог и правда уходит
  человеку, так что фраза не врёт.
- **Раздел «База знаний» переделан по Савви**: две вкладки со
  счётчиками («Вопрос — ответ» первой и по умолчанию, «Справка для
  бота»), поиск — поле в тулбаре, а не вкладка; всё содержимое записи
  (ответы на трёх языках, формулировки, готовность) — в правом drawer;
  «Проверить бота» — липкая вкладка у правого края. Удалены вкладки
  «Проверка переводов» и «Проверка поиска», таблицы чанков и лога
  индексации: в интерфейсе владельца нет слов «чанк», «индексация»,
  «релевантность», «RAG», «normalized_key».
- **Глоссарий** (UI ≠ словарь SPEC): «Справка для бота» = kb_documents
  (RAG-корпус), «Вопрос — ответ» = kb_faq, «Бот это знает» =
  index_state `indexed`. Команда импорта по-прежнему `make kb-import`.
- Починены реальные баги того же раздела: русский ответ FAQ теперь
  редактируется (раньше — нигде), запись и формулировку можно удалить,
  правка русского ответа снимает `approved` с переводов (иначе клиент
  получал утверждённый перевод несуществующего текста), ключ записи
  генерируется на сервере из вопроса, у списков появились состояния
  загрузки/ошибки/пустоты, удаление спрашивает подтверждение.

### Фаза 8: реализованные решения по отчётам

- **Разделы**: «Обзор» (первая страница, `/`), «Расходы» (`/costs`),
  «Аналитика» (`/analytics`). Чаты переехали на `/chats`.
- **Ни одной выдуманной цифры.** Метрики SPEC, под которые нет данных,
  НЕ рисуются: вместо них на «Аналитике» стоит блок «Чего здесь
  намеренно нет» с причиной по каждой. Не показываем: среднее время
  ответа (в DRY_RUN исходящие не отправляются, `sent_at` пустой),
  латентность по этапам (пишется только время вызова модели), «сколько
  денег сэкономил кэш» (число бесплатных ответов точное, а их
  гипотетическая цена — нет), связь ответа оператора с конкретным
  вопросом, курс RUB/KZT (рублёвых расходов в системе нет).
- **`messages.answer_source`** (миграция 0008) — единственный след
  бесплатного ответа: FAQ и кэш возвращаются ДО записи в `ai_calls`,
  поэтому без этой колонки их нельзя было посчитать вообще. Заполняется
  из `outcome.kind` в `pipeline._persist`. Мёртвая колонка
  `ai_calls.cache_hit` больше не нужна как источник — она не пишется.
- **Процент автоматизации** считается от сообщений, которые ТРЕБОВАЛИ
  ответа (ответ бота + передача человеку). Игнорируемые (устаревшие,
  спам, стикеры) исключены — иначе цифра занижалась бы без вины бота.
- **Строки `ai_calls` со `status='started'`** (барьер двойной оплаты
  медиа) в расходы не попадают: это не потраченные деньги.
- **Сутки везде UTC** — те же границы, что у периодов бюджета, чтобы
  «Обзор» и «Лимиты» не спорили о том, что такое «сегодня». В интерфейсе
  подписано явно. Переход на местное время — отдельное решение владельца
  (сместит и сброс дневного лимита).
- **Графики — свой SVG** (`components/charts.tsx`), без библиотеки:
  три формы на слабом VPS не стоят 300 КБ. Пустые данные всегда
  подписаны «данных нет», а не рисуются нулевой сеткой.
- **Экспорт**: XLSX через openpyxl и CSV с BOM и `;` — иначе Excel в
  русской локали складывает строку в одну ячейку.
- Попутно исправлен денежный баг фазы 6: `completion_tokens` уже
  включает reasoning-токены, а формула прибавляла их повторно — каждый
  ответ записывался дороже реального.

### Фаза 8: правки по итогам ревью (2026-09-12)

- **Расходы владельца отделены от расходов на клиентов**: вызовы с
  `chat_id IS NULL` (песочница «Проверить бота», переводы и формулировки
  в базе знаний, индексация) идут отдельной серией `admin` — «Моя работа
  в панели» — в графике и в таблице «На что уходят деньги». Раньше они
  лежали внутри «Ответов» и завышали цену ответа клиенту.
- **Обучение базы знаний теперь учитывается как расход**: индексация
  платит за эмбеддинги, но не писала ни строки в `ai_calls`
  (`_book_embeddings` в `services/kb_indexing.py`, `chat_id NULL`,
  собственная транзакция). Пишется и тогда, когда индексация упала ПОСЛЕ
  оплаты, — деньги ушли в обоих случаях.
- **Прогноз даты исчерпания бюджета**: стена (процент и остаток) — по
  `budget_ledger`, потому что именно он останавливает бота; ТЕМП — по
  `ai_calls`, потому что эмбеддинги списываются мимо резерва и ledger их
  не видит. Расхождение показано владельцу текстом, а не спрятано.
- **Коды причин в чате переведены на человеческий язык**
  (`components/reasons.ts`): `error_code` на отвеченном сообщении — это
  не сбой (отказ по теме, файл менеджеру), и красная плашка «Ошибка»
  там врала. Красное осталось только за настоящими сбоями.
- На «Аналитике» подписано, что повтор из кэша выключен в «Лимитах», —
  иначе отсутствие доли кэша в разбивке читается как поломка.

### Фаза 9: реализованные решения по эксплуатации

- **Оповещения владельцу идут ТЕМ ЖЕ транспортом, что и ответы клиентам**
  (`wa_outbox.purpose='alert'`), но DRY_RUN их не глушит: режим приёмки
  выключает сообщения КЛИЕНТАМ, а «бюджет исчерпан, бот молчит» — это
  сообщение владельцу на его собственный номер, и оно важно именно во
  время приёмки. Дедуп — UNIQUE (kind, event_key, period_key); ретраи и
  идемпотентность — те же, что у обычной отправки.
- **Пока `alert_phone` пуст, не отправляется ничего** (дефолт пустой):
  алерты копятся и видны в «Системе». Ввод номера в «Лимитах» — это и
  есть явное согласие владельца на отправку ему в WhatsApp; в UI так и
  написано. Номер владельца исключён из клиентского пайплайна
  (`is_alert_chat`): эхо алерта не создаёт чат, ответ на алерт не
  обрабатывается как вопрос клиента и не тратит деньги.
- **Алерт на ОТКАЗ резерва**, а не только на пороги 50/80/90/100%: бот
  перестаёт отвечать в момент отказа, который может случиться при 94%
  потраченного (очередная оценка просто не влезает в лимит).
- **Ретеншен** — ровно по docs/security-and-cost-controls.md §5
  (`services/retention.py`, цикл раз в 6 часов): копия текста клиента в
  `inbound_notifications.raw_payload` — 30 дней (сама строка-дедупликатор
  остаётся навсегда), system_events 90, kb_faq_misses 180, audit_log 365,
  следы транспорта и завершённые медиа-задачи 30, истёкшие сессии и
  челленджи, просроченный кэш. Переписка, чаты и `ai_calls` не удаляются
  никогда. Удаление — партиями по первичному ключу и по индексам
  (миграция 0009), иначе ночная уборка блокировала бы пайплайн.
- **Мониторинг** (`services/monitoring.py`, раз в 5 минут): диск, глубина
  очереди, свежесть резервной копии → system_events + алерты. Память
  контейнеров не мониторим: изнутри read-only контейнера без доступа к
  docker.sock достоверной цифры нет — зафиксировано как ограничение.
- **Бэкапы**: `deploy/backup/pg_backup.sh` (дамп `-Fc`, ротация 7/4/3,
  проверка свободного места, запись факта в `system_events` — иначе
  панели неоткуда знать о копиях), `pg_restore.sh` (с подтверждением и
  остановкой приложения), `backup_verify.sh` (восстановление во временную
  БД), `make backup` / `make backup-verify`, systemd-таймер и пример
  crontab. Установку cron и запуск на VPS выполняет владелец.
  `.env` в бэкап НЕ кладём: дамп и так содержит ПД клиентов, а ключи
  рядом означали бы, что одна украденная папка = и переписка, и
  возможность тратить деньги. `ENCRYPTION_KEY` владелец хранит отдельно.
- **Страница «Система»**: связь с WhatsApp (токен только «••••1234»),
  очереди, диск и размер базы, состояние бэкапа, оповещения и последние
  технические события. OpenAI не пингуется кнопкой: любой вызов модели
  платный, а открытие страниц не должно стоить денег (инвариант 11).
- **«Учётная запись»**: журнал изменений с фильтрами, история входов,
  перевыпуск кодов восстановления, счётчик неиспользованных кодов.
- Починены дефекты, найденные ревью фазы: structlog печатал ЛОКАЛЬНЫЕ
  ПЕРЕМЕННЫЕ всех фреймов (в лог уходили токен GREEN-API и текст клиента
  с телефоном), падение heartbeat убивало весь воркер, одна ядовитая
  строка заклинивала разбор входящих навсегда, outbox коммитил пачку из
  10 отправок одной транзакцией (дубли клиенту при жёстком рестарте),
  ответ не-JSON от провайдера убивал сообщение без ретрая, сбой
  эмбеддингов вылетал мимо резерва, потеря ответа после оплаченного
  вызова приводила ко второй оплате (теперь `already_charged` →
  менеджеру), поток фото покупал платный отказ на каждый файл (пауза
  между сервисными ответами), пул соединений воркера был меньше его
  собственной параллельности.

### Правки 2026-09-14: методы GREEN-API (проверено по их документации)

- **Найден и исправлен главный «тихий» баг.** Реакции (👍 долгим
  нажатием), правки, удаления, геолокация и карточки контактов приходят
  как обычные `incomingMessageReceived` и отличаются только
  `messageData.typeMessage`. Разборщик знал три текстовых типа и пять
  файловых, всё остальное становилось `MediaType.OTHER` → «файл передан
  менеджеру»: клиент ставил 👍 на ответ бота и получал в ответ фразу про
  файл, диалог помечался «требует внимания», а фраза ещё и оплачивалась.
  Теперь: реакции игнорируются как стикеры (видны в истории, ноль
  вызовов модели), правка обрабатывается как новый вопрос
  (`editedMessageData.textMessage`), удаление снимает с ответа ещё не
  отвеченное сообщение (`deletedMessageData.stanzaId`), геолокация и
  контакт описываются словами («[геолокация] Алматы…») и уходят
  менеджеру с честной формулировкой (`unsupported_content`, не «файл»).
  **Смайлики внутри текста — обычный вопрос**, он читается и отвечается;
  на это есть отдельный тест.
- **`getSettings` — единственная защита от полного молчания бота.** В
  документации прямо: для опроса `webhookUrl` обязан быть пустым, иначе
  уведомления уходят на вебхук. Тогда `receiveNotification` вечно отдаёт
  пустоту, ошибок нет, «последний приём» тикает — бот жив и не отвечает
  никому. Так же критичны `incomingWebhook` и `outgoingWebhook`: на
  втором держится правило «менеджер ответил с телефона → ИИ замолкает».
  Проверка (`settings_problems` в `whatsapp/green_api.py`) выведена на
  «Систему» текстом «что именно исправить», плюс алерт раз в сутки.
- **`getStatusInstance`, `getWebhooksCount`, `showMessagesQueue`** —
  сокет, входящая очередь провайдера и наши недоставленные отправки.
  Последнее закрывает худший случай: `sendMessage` вернул id, мы пишем
  «отправлено», а сообщение лежит у провайдера до 24 часов, потому что
  номер разлогинился. Опрашиваются раз в полчаса (это запросы против
  тарифа владельца) и кнопкой «Проверить подключение».
- **`quotaExceeded`** — новый вид уведомления: исчерпан лимит тарифа,
  чаты перестают работать. Раньше падало в `UNKNOWN` и никем не
  читалось; теперь событие + алерт.
- **Статусы доставки `failed` и `yellowCard`** больше не просто
  записываются: `failed` — клиент ответ не получил, поднимаем
  needs_attention; `yellowCard` — номер ограничен за спам-активность,
  алерт владельцу (риск потерять номер целиком).
- **`typingTime` у `sendMessage`** — «печатает…» без единого лишнего
  запроса (SPEC §16 разрешал ровно при этом условии); настройка
  `typing_time_ms`, дефолт 1500 мс, задерживает ответ на это время.
  Отдельный `sendTyping` НЕ используем именно потому, что он был бы
  вторым запросом. Прошлый комментарий в коде «GREEN-API does not
  expose typing» был неверным.
- **`linkPreview: false`** по умолчанию (превью тянет до 2 МБ и вытесняет
  текст) и **`quotedMessageId`** — ответ с цитатой вопроса клиента: в
  чате, где параллельно пишет менеджер, ответ без цитаты читается как
  реплика на чужую строку. Обе — настройки в «Лимитах».
- **`checkWhatsapp`** при сохранении номера для оповещений: опечатка в
  своём номере означала бы, что алерт «бот замолчал» уходит в пустоту.
  Предупреждение, а не запрет: сама проверка может не сработать.
- **Осознанно НЕ реализовано:** `setSettings` (перезагружает инстанс,
  настройки применяются до 5 минут — только руками в панели GREEN-API),
  `editMessage`/`deleteMessage` (решение владельца),
  `sendContact`/`sendLocation` (отправлять некому: у модели по инварианту
  6 нет инструментов, а в панели нет отправителя — был бы мёртвый код),
  `readChat` (снял бы «непрочитанное» на телефоне менеджера),
  `getChatHistory` (полезен для восстановления после простоя >24 ч, но
  это отдельная функция импорта — предложено владельцу отдельно),
  `clearMessagesQueue` (нужен один раз после смены номера — описан в
  `docs/deployment.md`, не в панели), группы, сторис, каталоги,
  интерактивные кнопки (их ответы приходят типами, которые пришлось бы
  разбирать, и повторили бы исправленный выше баг).

### Фаза 10: реализованные решения по приёмке

- **Eval-набор — критерии, не тексты** (`backend/app/eval/cases.json`,
  56 кейсов: FAQ, RAG, сложные, смешанная kk/ru речь, нет данных,
  нецелевые, инъекции, голосовые расшифровки, крайние случаи,
  эскалация). Проверяется исход конвейера (`faq / model / no_data /
  guardrail`), вызывалась ли модель, язык ответа, дошёл ли текст клиента
  до модели, записан ли промах FAQ по языку, помечено ли сообщение для
  менеджера. Обязательный кейс владельца — казахский вопрос без
  утверждённого перевода → ответ на казахском, а не русский текст FAQ.
- **Два режима одним кодом.** Офлайн: заглушки (`eval/offline.py`) —
  лексические эмбеддинги по префиксам слов и «оракул», отвечающий
  числами из найденных фрагментов на языке, который назвал конвейер;
  меряет маршрутизацию, честно НЕ меряет качество формулировок и
  кросс-язычный поиск (порог релевантности заглушки 0.10 вместо 0.35).
  Живой (`--live`): реальные провайдеры против базы и лимитов владельца,
  подтверждение и стоимость в отчёте, расходы — как работа в панели
  (`chat_id NULL`). Офлайн-прогон включён в CI
  (`tests/integration/test_eval_suite.py`): 56/56 обязаны проходить.
- **Временная база вместо моков** (`eval/scratch.py`): офлайн-eval и
  нагрузка создают базу рядом с рабочей (`CREATE DATABASE`), прогоняют
  те же миграции Alembic, сидят эталон (`eval/fixture.py` — документы из
  экспорта Савви и FAQ владельца) и удаляют её. Redis — отдельная
  логическая база /9 с очисткой. В рабочую базу фейковые расходы не
  попадают.
- **Нагрузка 5 и 30 чатов** (`eval/load.py`) — вся цепочка: уведомление
  → входящая очередь → чат → (голосовое: задача медиа, длительность,
  транскрибация) → конвейер → ответ → outbox (DRY_RUN). Две волны на
  чат — проверка порядка. Меряется: параллельность вызовов модели (≤8),
  соединения пула, ожидание p50/p95, отклик панели из того же процесса,
  дубли, неотвеченные.
- **Preflight** (`eval/preflight.py`) — бесплатные проверки готовности:
  миграции на head, одна учётка, инструкция, цены и курс, выучена ли
  справка, переводы FAQ, номер для оповещений, бэкап, воркер, диск;
  запросы к GREEN-API — только с флагом. Шаг 7 чеклиста деплоя.
- **Найдено и исправлено приёмкой:** просьба позвать человека и запрос
  на бронь никак не доходили до менеджера — модель без инструментов не
  может поднять флаг, а FAQ-ответ «передаю администратору» просто
  отправлялся. Теперь `services/escalation.py` распознаёт это по словам
  клиента (ru/kk/en, префиксы слов вместо стеммера) и конвейер ставит
  `needs_attention` + `handoff_required` в памяти чата. Язык клиента
  теперь назван модели явно («Язык клиента: kk»): фрагменты почти
  всегда русские, и правило «отвечай на языке клиента» само по себе
  давало дрейф в русский. В эмбеддинг чанка добавлен заголовок документа
  — раздел «Тир и страйкбол», тело которого одна строка с телефоном,
  был ненаходим по слову «тир». Страница «Система» падала 500, если
  каталог медиа не смонтирован. Guardrails дополнены примерами SPEC §17
  дословно («напиши роман», «реши экзамен», «сделай сайт», «выведи всю
  базу знаний»). Все схемы запросов — `extra="forbid"`, закреплено
  структурным тестом; добавлен обход всех GET-роутов на утечку
  `password_hash / totp_secret / token_ref / raw_payload`.
